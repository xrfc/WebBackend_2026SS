# 可视化实验室：原理演示与真实观测

运行 `python scripts/deploy.py` 后访问 `http://localhost:8000/lab`。配置了不同网关端口则使用相应端口。页面随网关容器交付，所有样式、脚本来自本服务，无需 Node、前端构建或外部资源。

## 1. 原理演示怎么用

选择场景，通过下一步、上一步、回到开头推进；桌面也可直接选择左侧步骤。每一步显示：

- Redis：活动剩余、本用户去重记录、Stream 事件。
- RabbitMQ：未完成消息、死信和同请求 ID 的重复消息。
- MySQL：已提交订单和商品可用库存。
- 当前处理动作、设计原因、验证方法、示意数据及代码位置。
- 面试追问与展开思路。

默认示意商品总库存 5、活动预留 3、商品可用 2；请求 R1、订单 O1 是教学标签，不是合法 API UUID。数字并非当前部署数据。切换场景重置演示状态，不会调用抢购接口、创建商品、停止服务或重投死信。

| 场景 | 需要看清的变化 |
|---|---|
| 正常下单 | 受理、投递、订单提交是三种成功；先 commit 后 ACK |
| 重复点击 | 同活动同用户取回原请求，不再次扣库存 |
| MQ 中断与恢复 | Stream 保留，恢复投递后才生成订单 |
| relay 清理前退出 | 产生重复消息，用唯一约束保持订单唯一 |
| 消费者提交后退出 | O1 保留，重投后取回已有订单 |
| 数据库故障 | 有限重试、死信、manual_review，不盲目退款或退库存 |
| 关闭活动 | 先冻结，未售额度只回收一次，旧受理继续处理 |
| 关闭事务失败 | 冻结保留，修复后重复关闭恢复事务 |
| 初始化失败 | 原活动和预留保留，后台恢复，不重复预留 |
| Redis 记录遗失 | 库存未知，不按初始库存自动重建 |
| 极端输入 | 422/503 在修改之前拒绝，Lua 错误不是事务回滚 |
| 积压上限 | 原积压保留，新 R1 在扣库存之前拒绝 |

演示是离散状态解释，并不模拟全部网络时序、磁盘错误或性能。不能把这些数字写成压测结果。

## 2. 真实观测怎么用

使用 `.env` 中管理员账号登录“真实观测”。普通用户不能调用观测接口；服务端也校验角色和 Token 撤销，不能仅靠隐藏按钮限制权限。

默认手动刷新，也可勾选每 5 秒刷新；离开页面标签或浏览器隐藏时暂停定时采样。页面没有使用 localStorage/sessionStorage 保存 Token。刷新浏览器后需要重新登录；注销调用服务器撤销，若服务器不可用，本页仍清除凭据并明确提示撤销失败。

实际数据包括：

1. 五个后端 `/ready` 的就绪状态与这次检查耗时。就绪不代表 MQ 所有统计或业务交易都已成功。
2. Stream `XLEN`、consumer group pending、上限和前 10 条合法事件预览。
3. MQ 主、重试、死信队列的 `messages_ready`、`messages_unacknowledged`、`messages`。通过内部 15672 management API 读取，不把该端口暴露到主机；统计可能延迟，缺字段时显示未知。
4. 最近最多 25 个活动：SQL 初始额度/状态/已释放、Redis 剩余/去重人数/状态、唯一订单数、商品可用库存。
5. 最近 20 张已提交的秒杀订单，以及按原请求 UUID 核查 SQL 和 Redis 证据。

按请求核查时 SQL 订单优先。Redis 原始记录过期不代表已提交订单消失。没有单条 MQ 逐请求追踪，因此不会以 Stream 不在预览、MQ 总量为零等条件宣称某条消息已完成投递。

## 3. 如何解读不一致

跨 SQL、Redis、MQ 依次/并行采样，**不是跨存储原子快照**；持续交易时数量可能短暂不一致。MQ 总量与 Stream 总量属于整个应用，不是当前活动或当前请求的数量。订单面板仅展示最近活动，不能当作全部历史订单统计。

Redis Key 缺失、类型错误或库存格式异常时显示未知，不能显示为正常零库存。MQ 不可读取或管理统计尚未初始化也显示未知。刷新失败保留最近成功样本，并明确标记旧数据；会话失效则清除实际数据并要求重新登录。

正常、仍保留完整记录的活动可核对：`初始额度 = Redis 剩余 + 已受理用户数`。关闭活动后的 Redis 剩余可能是已释放额度的历史值，不能再次当作可售库存。请求记录在活动结束后 7 天到期，之后该等式的 Redis 证据可能不完整。最终订单以 SQL 为准。

## 4. 真正做一次故障实验

只能在隔离测试环境执行，页面本身不会停止服务。

1. 管理员通过 `/docs` 创建商品和活动；普通用户登录并提交抢购，保存返回的 `request_id`。
2. 在面板按请求 ID 查询，核对最终订单与价格。重复提交确认同一个请求和一张订单。
3. 新建另一活动，先执行 `docker compose stop rabbitmq`，再让普通用户提交。
4. 确认请求受理但尚无订单，实际 Stream 保留事件；刷新读取受理证据。
5. 执行 `docker compose start rabbitmq`。恢复消费/接管可能需要等待，按原请求 ID 查询直到 created。
6. 确认最终订单恰好一张。等待过长或出现 manual_review 则查看日志和死信，不自动增加库存。

自动两阶段实验在 `tests/test_faults.py`，由 CI 控制停止和恢复。页面故障模拟与自动故障测试是不同的证据来源。

## 5. 接口和资源限制

- `GET /seckill/observe/overview?limit=25`：管理员；limit 1—50，每管理员 36 次/分钟。
- `GET /seckill/observe/requests/{request_id}`：管理员；每管理员 30 次/分钟。
- `GET /lab/api/health`：管理员；每管理员 36 次/分钟。

观测响应 `Cache-Control: no-store`。页面 CSP 限制脚本、样式与 API 同源，商品名称等不可信数据使用 textContent 渲染。观测不会使用 Redis KEYS、遍历全部抢购记录、消费 MQ 消息、删除事件或修改库存。活动、订单和 Stream 预览都有数量上限。

management API 沿用当前 RabbitMQ 应用账号。单机学习环境可用；正式环境应拆出权限受限的观测账号与监控系统，不能据此宣称高可用或完整分布式链路追踪。

## 6. 验证页面

```bash
python -m pytest -q
npm run test:scenarios
# 完整隔离栈已启动；读取本机 .env 的管理员凭据
npm ci
npx playwright install chromium
npm run test:ui
```

场景测试检查库存、重复、回收与未知数据等关键不变量；Chromium 验收实际桌面/手机交互、真实管理员采样、请求核查和注销，并额外模拟数据不可用/旧数据/会话过期及不可信商品名称。CI 保留演示截图；模拟故障样本不能算作真实系统故障注入。
