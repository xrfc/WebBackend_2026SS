# 部署与异常处理：从课程演示到可恢复服务

## 1. 一键启动实际做了什么

`python scripts/deploy.py` 先检查 Docker/Compose，生成随机 `.env`（重复运行保留），再构建镜像并等待中间件就绪。`db-init` 使用 MySQL 命名锁初始化/升级表并创建管理员；其他服务等待它成功。五个业务服务就绪后启动网关，网关 `/ready` 检查所有后端。`/health` 只表示进程存活，不能拿它冒充依赖就绪。

MySQL、Redis、RabbitMQ 分别使用数据卷；Redis AOF 使用 `appendfsync always` 与 `noeviction`，避免秒杀记录被当作普通缓存驱逐。代价是每次写入的持久化成本更高；本版本首先保证学习实验的结果可解释，不宣称峰值吞吐。容器日志限制滚动大小。首次镜像下载时间不属于业务启动性能。

网关复用 HTTP 连接池，转发真实状态码和普通响应体，区分 502（无法连接）与 504（超时）。请求体最大 64 KiB，字段长度/ID/页码均有上限。用户/权限仍由目标服务检查，不能只依赖网关。

## 2. 三个不同的成功

- **受理成功**：Lua 已将库存、用户去重、原始消息和请求记录写入 Redis，HTTP 202。
- **消息投递成功**：RabbitMQ 确认消息，relay 才确认并删除 Stream 项。
- **订单成功**：MySQL 已提交订单，查询返回 `created` 和订单 ID。

HTTP 超时不能证明后台失败。客户端应保存活动 ID、请求 ID，查询结果；再次提交同一活动会返回同一用户的原请求，避免一次按钮重试变成两张订单。

结果查询也有跨库采样窗口：第一次 SQL 查询没有订单，之后消费者可能提交并将 Redis 更新为 created。遇到这种情况，查询会开启新的 SQL 事务重新确认，避免 MySQL REPEATABLE READ 的旧快照，也避免返回 created 却没有 order_id。再次查不到订单则业务接口返回 503，管理员观测标记不一致并要求核查。

## 3. 为什么持久消息还要 Stream 和幂等

原版“Redis 扣库存 → RabbitMQ 发布”存在间隙。现在 Lua 把待发布事件写入 Stream，与库存修改同脚本执行；relay 网络失败后事件仍在。relay 使用 consumer group，30 秒未处理的 pending 项可被接管。

另一个间隙仍存在：RabbitMQ 已收到消息，但 relay 在删除 Stream 前退出。恢复后会重投。消费者将消息的稳定 `request_id` 写入唯一索引，相同事件多次到达只取回已有订单；第二个唯一索引限制每活动每用户一单。数据库提交后、确认前退出，也由这一机制处理。

Lua 是顺序原子执行，并不是运行时错误的事务回滚。本版本在修改前检查相关 Key 类型与库存/价格数据；专用命名空间不允许其他业务修改。Redis内存/磁盘/持久化错误仍应报警并对账；不要把“Lua原子”解释成“任何基础设施故障都不会丢数据”。

## 4. 活动库存如何核对

创建活动：商品可用库存减少 N，活动获得 N 的预留额度。抢购仅在活动额度中扣减。正常状态下：

`活动初始额度 = Redis 剩余额度 + 已受理请求数量`

订单全部落库后再核对唯一订单数量。商品详情展示可用库存；抢购库存查看秒杀接口。

关闭活动先冻结 Redis，阻止新抢购，再在同一个数据库事务中释放未售额度并标记关闭。数据库失败时 Redis 继续保持冻结，重新关闭可恢复；已关闭则返回原结果，不再次释放。已受理但待处理的额度保持占用。

如果已开启活动的 Redis 状态消失，不能从初始额度重建：那会忘记已经出售的额度。系统返回 503 并停止回收库存，管理员需要根据订单、Stream、MQ、请求记录和备份确认结果。初始化失败则由后台重试；管理员可以按活动 ID 关闭未开始受理的初始化活动。

## 5. 消费失败与死信的操作

可重试的数据库/连接异常：最多 3 次、每次 5 秒延迟。无法解析、价格/商品/活动与记录不一致等消息直接转入 `order_dead_queue`。转发确认后才能确认原消息；转发失败则原消息重新入队。

`manual_review` 表示自动处理已停止。不要据此直接增加库存：可能存在先前提交成功但通知失败的订单。核查流程：

1. 用请求 ID 查 `orders`，确认是否已存在最终订单；检查活动和原始抢购记录。
2. 查看服务日志中的请求 ID、错误类型和死信队列，修复数据库/记录根因。
3. 对仍有完整且合法原始记录的请求，用原 ID 重投：

```bash
docker compose exec seckill python -m scripts.replay_order --request-id 请求UUID
```

脚本只重投前 100 条死信内匹配的一条合法事件，并在发布确认后确认该死信；其他事件保持。它不会自动构造缺失活动/库存记录，也不会批量清空队列。重投后查询最终订单，确认一张；如果库存、记录或事件永久损坏，保留证据再进行人工补偿。

## 6. 边界值为什么这样设

库存整数 0—100000（活动额度至少1）、ID 1—2147483647，与 MySQL Integer 存储一致。使用 StrictInt，避免把 `true` 或字符串悄悄转成库存。金额 0.01—99999999.99、最多两位小数；请求用 Decimal，Redis/MQ用整数分，数据库用 DECIMAL，API以字符串返回精确值。NaN/Infinity/额外小数明确拒绝，不静默舍入新交易。

默认活动最多24小时，可提前24小时创建。活动时间在 Redis Lua 内以 Redis TIME 检查，避免各服务时钟不一致。商品预留与状态操作采用相同的数据库锁顺序；活动中不允许直接覆盖商品库存或下架。

秒杀请求默认每用户每秒30次；出站积压上限10000，Uvicorn在途上限有限。售罄、重复、429、503需要单独统计；把全部拒绝响应都计为成功下单会夸大容量。

## 7. 鉴权、推送与 AI 的边界

JWT包含sub/role/exp/iat/jti，Redis按jti记录撤销且保留到Token到期；认证Redis不可用时返回503，不直接放行。旧Token需要重新登录。密码bcrypt有72字节限制，中文字符按UTF-8字节校验。

WebSocket连接先验证Token和路径用户，浏览器来源需允许。每用户5连接、每条32通知积压、发送2秒上限；慢连接关闭，结果仍可查询。跨实例通知使用Pub/Sub，断连期间不保证补推，因此持久查询才是权威。Token过期/撤销最多20秒内再次检查。

AI设置独立超时、8个进程内调用槽位、有限等待。接口显式区分正常模型回复与`not_configured`/`overloaded`/`upstream_unavailable`降级。调用槽位属于单进程，多个AI实例不能据此宣称全局并发限制。提示词约束不能保证模型永远不编造，交易价格不从AI答案读取。

## 8. 如何确认测试真的有效

单元测试验证输入边界、金额、状态、去重、关闭回收、权限、消费转发行为；fakeredis/SQLite用于隔离。真实测试通过网关 HTTP 请求和实际 Redis/RabbitMQ/MySQL，检查最终订单数量、金额、越权、注销、WebSocket。CI重复服务重启验收，并停RabbitMQ受理请求、恢复后确认只落一单。

没有再使用固定True作为验收。异常测试必须观测到429/503/死信等实际结果，恢复后验证订单数量；只打印“PASS”不算证明。测试环境的历史数据/正常用户不应被清空，性能测试另做，不继承旧版7980数字。

## 9. 升级和回退

升级前停止旧版抢购，备份MySQL、Redis、RabbitMQ及`.env`。确认原数据库卷名称：本Compose项目名固定为`webbackend`；旧版默认卷可能是其他前缀，不能看到新库为空就以为旧数据被删除。按旧Compose配置导出/导入，或显式绑定已有卷，再运行初始化。

旧订单加可空字段，历史订单没有可推断的活动ID；MySQL旧Float金额迁移按分舍入。DDL可能部分完成，初始化可重跑，但不保证一条命令回退所有DDL。需要回退时停止新请求，使用备份和原代码版本整体恢复，不能仅回退Python文件忽略库存/MQ状态。

本项目尚未实现支付、付款超时取消/退款、跨机房高可用；单Redis/单RabbitMQ/单MySQL仍有基础设施边界。重建容器保留数据卷，与磁盘整体损坏是不同故障。超过活动结束7天的悬挂请求需要人工核查；不要把延迟无限长的订单自动计为失败并退库存。
